IAM covers **operators and services** on AWS. **Your application's users** (customers signing in to your app) need something else: **Amazon Cognito**, or an identity provider such as Auth0 or Okta.

## Cognito's two parts

| Part | Does | Output |
|---|---|---|
| **User pool** | Sign-up, sign-in, MFA, password reset, Google/Apple login (OIDC/SAML) | **JWTs**: ID, access and refresh tokens |
| **Identity pool** | Exchanges a token (from a user pool, Google…) for **temporary AWS credentials** tied to an IAM role | Short-lived keys to call S3, DynamoDB… directly |

## Protecting APIs

| Option | When |
|---|---|
| **JWT authorizer** (HTTP API) / **Cognito authorizer** (REST API) | Tokens from Cognito or any OIDC provider — no code |
| **Lambda authorizer** | Custom logic: own API keys, special headers, database checks |
| **IAM (SigV4)** | Service-to-service calls, or clients holding identity-pool credentials |

The standard flow for web/mobile is **Authorization Code + PKCE**: redirect to sign-in, receive a code, exchange it for tokens. Never ship a client secret inside an app.

<Callout type="key">
**Access tokens** call APIs and are short-lived (e.g. 1 hour). **Refresh tokens** get new ones, live longer and must be protected. Never treat the ID token as the "permission" to call an API.
</Callout>

## Common mistakes

- Over-broad IAM roles for identity-pool users (one role that can write *every* S3 object). Scope by `${cognito-identity.amazonaws.com:sub}` so each user only touches their own prefix.
- Building your own login and password storage — easy to get wrong, rarely worth it.
- Forgetting Cognito bills per **MAU**: the first 10,000 are free, then per user.
