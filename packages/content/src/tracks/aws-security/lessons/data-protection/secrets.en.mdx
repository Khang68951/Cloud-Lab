Database passwords, third-party API keys, private keys… are **secrets**. Rule number one: **never put secrets in code, git, AMIs, or plaintext environment variables**.

## The two main options

| | **Secrets Manager** | **SSM Parameter Store** |
|---|---|---|
| Encryption | KMS | KMS (`SecureString` type) |
| Automatic rotation | **Yes** (built in for RDS, Redshift, DocumentDB; custom via Lambda) | Not built in |
| Cross-Region replication | Yes | No |
| Price | $0.40 per secret/month + $0.05 per 10,000 calls | Standard parameters **free** |
| Fits | Database passwords, credentials that must rotate | Configuration, feature flags, rarely changing secrets |

## Using them correctly

1. The secret lives in Secrets Manager or Parameter Store.
2. The app (EC2, ECS, Lambda) has an **IAM role** that can read only the secrets it needs.
3. The app reads the secret at start-up, **caches it in memory** for a few minutes, and refreshes when needed.
4. ECS and EKS can inject secrets into containers; RDS can even manage its master password in Secrets Manager.

<Callout type="key">
Rotation is only safe if the app **always reads the current value**. An app that reads the secret once at boot and keeps it forever breaks after the first rotation.
</Callout>

## Common mistakes

- Committing a `.env` file to git — bots find it in minutes, and deleting the commit does not remove it from history.
- Logging secrets while debugging.
- A role with `secretsmanager:*` on `*` when the app needs one secret.
